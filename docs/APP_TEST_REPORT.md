# 앱 시나리오 테스트 결과

검증일: 2026-09-09. 개발 서버 `http://localhost:3000`, 현재 프로젝트 코드 및 연결된 Atlas DB 기준.
기존 사용자 모임에는 쓰기 작업을 하지 않고 `QA_0909_` 모임을 별도로 사용했다. 실제 CLOVA 유료 호출과 실제 송금은 수행하지 않았다.

## 테스트 요청을 확장한 범위

혼자하기/함께하기의 로그인 → 모임 생성 → 참여자 입력/초대 → 대기/활성화 → 영수증 등록 → 소비자 선택 → 수정/삭제 → 정산 완료 순서를 확인한다. UI뿐 아니라 API 권한과 DB 저장 결과도 확인한다. 초대 중복/재발급/동시 요청, 게스트 다중 모임, 잘못된 금액/수량/소비자, 완료 후 변경, OCR 입력 제한을 추가 검사한다. 재현한 문제와 코드상 위험을 구분하며, 사용자가 지정한 수정 외에는 임의로 변경하지 않는다.

## 실행 결과 요약

- 자동 테스트: 수정 후 `npm test` **10개 통과**.
- 정적 검사: `npm run lint` 통과. `git diff --check` 통과.
- 주요 API/DB 시나리오: 수정 전 35개 중 33개 통과. 게스트 다중 모임과 엄격한 개인별 조회 조건 불충족.
- 게스트 수정 후 주요 API/DB 시나리오: 기존 항목과 호환/권한 검사를 합친 **39개 중 38개 통과**. 남은 1개는 다른 참여자 영수증이 응답에 포함되는 조건이다. 조회 정책 결정이 필요하다.
- 추가 API/계산 검사: **13개 중 10개 통과**, 입력 검증 관련 3개 문제 발견.
- 위 추가 검사 중 금액 배분 검사는 인원 1~50명 × 금액 7종 = **350개 조합**의 합계 보존·1원 이내 차이를 확인했다. OCR 정확도나 전체 앱의 완전성을 의미하지 않는다.
- 운영 빌드는 실행 중인 개발 서버의 `.next`와 충돌할 수 있어 이번 테스트에서 수행하지 않았다.

## 수정 완료: 게스트가 다른 모임에 들어가면 이전 모임 접근 상실

### 원인과 재현

1. 비회원으로 A 모임에 참여하면 `dutchpay_guest`가 저장됨.
2. 같은 브라우저로 B 모임에 참여하면 같은 이름의 쿠키를 B 토큰으로 덮어씀.
3. A 모임의 API 요청에서 B 토큰이 전달되어 401 발생. 실제 요청으로 재현했다.

### 변경

- 새 쿠키 이름: `dutchpay_guest_<groupId>`.
- 읽기: 해당 모임 쿠키 우선, 없으면 기존 `dutchpay_guest` 사용.
- 적용: 모임 페이지, 모임 변경 API, OCR API, 초대 참여 쿠키 발급.
- 유지: HttpOnly, SameSite=Lax, 운영 HTTPS Secure, 30일 유효기간, 서버의 모임/해시/만료 검증.
- 기존 DB 구조/사용자 데이터는 변경하지 않았다.

### 수정 후 실제 검사

- A 참여 → B 참여 후 두 쿠키를 브라우저 방식으로 함께 전달: A/B 페이지 모두 200.
- B 참여 후 A 영수증 저장: 200.
- A OCR 요청: 인증 통과 후 빈 파일 검증에서 400. 유료 호출 없음.
- A의 기존 형식 쿠키와 B의 새 쿠키가 공존해도 A 조회 가능.
- A 토큰을 B 쿠키 이름에 억지로 넣으면 B 변경 요청 401.
- 과거에 이미 덮어써져 잃어버린 토큰은 자동 복구되지 않는다. 신원 확인 없이 닉네임만으로 기존 멤버 권한을 돌려주는 복구는 구현하지 않았다.
- 모임별 쿠키는 수십 개 이상의 동시 모임에서 브라우저 쿠키/헤더 용량 제한을 고려해야 한다. 그 규모가 필요하면 서버 측 브라우저 세션 한 개로 통합할 수 있다.

## 남아 있는 문제와 위험

### 실제 재현

1. **조회 권한 정책 확인 필요 — 다른 사람 영수증이 서버 응답에 포함됨.**
   - 위치: `lib/groups.js`의 `getGroupBoard`.
   - 게스트 영수증을 저장한 뒤 총대 페이지 응답 본문에서 그 가게 이름이 확인됐다. 화면은 사용자별 필터지만 데이터는 전체 전달이다.
   - “타인을 눌러 조회 가능”이면 현재 설계에 해당한다. “본인 것만 접근 가능”이면 P1 권한 문제이며 서버에서 제한하고 정산 요약만 별도 제공해야 한다.

2. **P1: 같은 영수증 내 중복 메뉴 `_id`를 허용함.**
   - 위치: `lib/groups.js`의 `normalizeReceipt`, `lib/settlement.mjs`의 `paymentAmount`.
   - `_id`가 같은 메뉴 두 개를 API로 전달하면 200 저장된다. 화면 키/메뉴 참조가 충돌하고 `.find()`는 첫 메뉴만 반환할 수 있다.
   - 이번 실행에서 중복 ID 허용을 재현했다. 실제 금액 오표시는 별도 재현하지 않았다. 서버 중복 검사 또는 서버 ID 관리가 필요하다.

3. **P2: 빈 단가가 0원으로 저장됨.**
   - `unit_price: ""`를 API로 전달하면 200. `Number("")`가 0이 되기 때문이다.
   - 화면 required와 별개로 서버에서도 빈 값과 명시적 0원을 구분해야 한다.

4. **P2: 깨진 JSON에 400 대신 500 반환.**
   - 모임 변경 API에 `{`만 전달하면 500. 입력 오류를 서버 장애처럼 취급한다.

### 코드 검토에서 확인한 위험 — 동시성/실기 재현은 별도 필요

- **정산 완료와 영수증 저장 동시 실행:** ACTIVE 확인이 저장 트랜잭션 밖에 있다. 완료 확인과 저장이 엇갈리면 완료 뒤 저장이 커밋될 가능성이 있다. 순차적인 완료 후 저장은 차단됨을 확인했지만 경쟁 상황까지 보장되지는 않는다.
- **ACTIVE 모임 실시간 갱신 없음:** 자동 새로고침은 WAITING에서만 실행된다. 다른 사람이 추가하거나 총대가 종료해도 기존 참여자 화면은 즉시 반영되지 않을 수 있다. 서버는 종료 후 요청을 거부한다.
- **비회원 참여 후 다른 계정 로그인:** `getGroupViewer`가 로그인한 회원 조회를 먼저 처리하고 실패 시 게스트 쿠키를 검사하지 않는다. 기존 게스트 권한을 유지할지 계정에 연결할지 정책/처리가 필요하다.
- **SOLO의 다른 결제자 입력 불가:** 모든 영수증은 조작자 본인 명의로 고정된다. 혼자 정리하며 친구가 결제한 것도 대신 입력하려는 요구와 충돌할 수 있다. 이는 함께하기의 본인 고정 요구를 지킨 결과이므로 모드별 정책을 확인해야 한다.
- **생성 후 사람 추가/목표 인원 변경 경로 없음:** 생성 시 참여자 입력과 정해진 인원 초대는 되지만 활성화 후 인원 변경/탈퇴는 별도 기능이 없다.
- **할인 금액:** OCR 실제 결제액과 메뉴 합계 차이는 경고하지만 저장값은 메뉴 합계다. 할인 배분이나 수량으로 나누어떨어지지 않는 할인은 사용자가 조정해야 한다.
- **사진 교체 중 OCR 요청:** 사진 선택/탭 변경과 진행 중 응답을 연결하는 취소/버전 검사가 없어 이전 사진 응답이 최신 입력을 덮을 가능성이 있다. 추가 재현 필요.
- **초대 링크 재접속:** 사용된 링크는 미사용 조건에서 제외된다. 기존 참여자에게 모임 화면으로 안내하는 재진입 경로를 개선할 여지가 있다.
